#+DESCRIPTION: How this Emacs configuration is structured and why

* Overview

This document explains how the Emacs configuration is organized, how different parts work together, and the reasoning behind major design decisions.

** The Big Picture

Think of this configuration as three layers:

1. *Foundation*: Spacemacs provides the base (layers, package management, keybindings)
2. *Custom Modules*: Org files that tangle to Elisp (themes, utilities) plus pure elisp modules like pasteboard integration
3. *Integration*: macOS-specific features, external tools (ripgrep, hunspell, enchant/aspell), custom workflows

* Architecture Components

** Core Structure

*** Spacemacs Layer
- *File*: =spacemacs.d/init.el= (=/Users/jay/emacs/emacs-settings/spacemacs.d/init.el=)
- *Purpose*: Configures Spacemacs layers and basic settings
- *What it loads*:
  - org layer (with org-roam support)
  - auto-completion layer
  - compleseus (completion framework)
  - spell-checking layer
  - osx layer (macOS integration)

*** Literate Programming Modules

These are the heart of the customization. Each =.org= file contains documentation and code blocks that tangle to =.el= files:

| Org File                                  | Generated File        | Purpose                           |
|-------------------------------------------+-----------------------+-----------------------------------|
| =shared-functions.org=                    | =shared-functions.el= | Core utilities (9,983 lines)      |
| =gnu-emacs-startup.org=                   | =gnu-emacs-startup.el= | Alternative startup config        |
| =org-authoring.org=                       | =org-authoring.el=    | Org-specific authoring helpers    |

*How it works*:
1. Edit the =.org= file (contains code + documentation)
2. Press =C-c C-v t= to "tangle" (extract code blocks → =.el= file)
3. Emacs loads the =.el= file on startup
4. Optional: Byte-compile =.el= → =.elc= for faster startup

Note: =pasteboard-copy-and-paste-functions.el= is now pure elisp and does not tangle.

** Loading Order

Understanding the loading sequence helps debug issues:

#+BEGIN_SRC
1. Emacs starts
2. Loads ~/.emacs.d/init.el (Spacemacs core)
3. Reads ~/.spacemacs.d/init.el (symlinked to /Users/jay/emacs/emacs-settings/spacemacs.d/init.el)
4. Spacemacs loads layers (org, auto-completion, etc.)
5. Loads spacemacs-new-config.el
6. Loads jay-osx.el (provides the early =key-minor-mode-map=)
7. Loads gnu-emacs-startup.el
8. Loads org-authoring.el
9. Loads spellcheck.el
10. Loads shared-functions.el (tangled from shared-functions.org)
11. Loads other modules (deferred or immediate based on config)
12. Loads local-config.el (if exists, gitignored for machine-specific settings)
#+END_SRC

*Why this order matters*:
- =jay-osx.el= must load before anything that uses =key-minor-mode-map=
- =org-authoring.el= must load before modules that call Org-specific authoring helpers, such as =spacecraft-mode.org=
- =spellcheck.el= must load before =shared-functions.el= so any remaining spellcheck callers or keybindings resolve against the dedicated spellcheck module instead of reintroducing split ownership
- =shared-functions.el= provides utilities used by other modules
- Some modules defer loading until needed (performance optimization)

* Key Design Patterns

** Literate Programming

*What*: Documentation and code live together in =.org= files.

*Why*:
- Code is easier to understand with surrounding context
- Natural place for design notes and examples
- Single source of truth (no separate docs to update)

*Example*:
#+BEGIN_EXAMPLE
,* Clipboard Cleaning Function
This function removes smart quotes and normalizes dashes
when pasting from web pages.

,#+BEGIN_SRC emacs-lisp
(defun pasteboard-paste-clean ()
  "Clean and paste clipboard content."
  (interactive)
  ...)
,#+END_SRC
#+END_EXAMPLE

** Adaptive Behavior

*What*: Functions detect context and adapt behavior automatically.

*Examples*:
- =pasteboard-paste-adaptive=: Routes clean pastes through =pasteboard-paste-clean= (one obvious clean path), pastes raw in code
- =smart-return=: Different behavior in org vs. code vs. text modes
- Font/theme functions: Adjust frame parameters without permanent changes

*Why*:
- Reduces cognitive load (don't think about mode-specific commands)
- Fewer keybindings to remember
- More "just works" behavior

** Centralized Utilities (Legacy)

*What*: =shared-functions.org= contains 300+ custom functions.

*Status*: Historically the single home for nearly all utilities. That stance has shifted — see [[*Keep Modularizing][Keep Modularizing]]. =shared-functions.org= is now treated as the *residue*, not the target: new subsystems are extracted to their own files, and existing coherent clusters (prose editing, Org authoring, spellcheck) are progressively moved out.

*Original rationale (still partially true)*:
- Easy to search (everything in one place)
- No dependency management between multiple files
- Emacs handles large files fine

*Naming conventions*:
- =jay/...= - User-facing interactive commands
- =pasteboard-...= - Clipboard-related functions
- =org-...= - Org-mode customizations
- =my-...= - Various utilities

** macOS Integration

*What*: Deep integration with macOS clipboard and system features.

*How*:
- =pbpaste= command retrieves clipboard → Emacs
- =pbcopy= command sends text → system clipboard
- Cleaning pipeline normalizes formatting between systems

*Why separate pasteboard module?*
- Complex logic (markdown/org detection, smart quote normalization)
- Platform-specific (only works on macOS)
- Isolates external dependencies

* Keep Modularizing

The single highest-payoff ongoing work in this config is splitting monolithic files into focused modules — one coherent subsystem per file. Recent examples: =spacecraft-mode.org= (prose editing), =org-authoring.org= (Org structure helpers), and =spellcheck.org= (Flyspell/Jinx/Hunspell + personal dictionaries). =shared-functions.org= is the monolith most future splits will come from.

This supersedes the earlier "one big file is fine" stance. That stance was defensible when it was written. Two things have changed since: the file has grown substantially, and AI-assisted editing has put a hard premium on focused context.

** The Concrete Payoffs

Each of these compounds every time you touch the subsystem.

*** Grep becomes navigation

When spellcheck lives in =spellcheck.org=, changing how Flyspell handles large buffers means opening one file and seeing the whole subsystem at once. In the monolith, you are scanning line 4,200 of 9,983 hoping you landed in the right block. The file-per-subsystem structure makes the file itself a form of navigation.

*** LLM context windows

This is the biggest modern reason, and it did not exist when the config was designed. When an AI assistant helps with spellcheck, loading a focused =spellcheck.org= gives it tight, relevant context. Loading =shared-functions.org= burns context on irrelevant code and forces the model to guess which sections matter. Post-split, AI help on that subsystem becomes sharper, cheaper, and more accurate.

*** Safe refactoring

A physical file boundary is a stronger guarantee than a conceptual one. Rewriting =spellcheck.org= wholesale cannot accidentally break Org authoring, because the Org authoring code is not in the file.

*** Git history tells a story

=git log --follow spellcheck.org= shows the evolution of exactly one subsystem. In the monolith, every commit touches =shared-functions.org= for unrelated reasons, and the file's history degenerates into noise.

*** The mental map stays accurate

You will remember that spellcheck lives in =spellcheck.org= forever. You will not remember that spellcheck lives "around line 4,200 of =shared-functions.org=" — that map rots the moment the file grows.

** Why This Beats the Alternatives

- *Switching frameworks* (Spacemacs → Doom): weeks of disruption, mostly theoretical benefit. Modularizing: hours of work, compounding benefit.
- *Deprecated function cleanup*: a maintenance tax you pay once. Modularizing: a structural gain that pays out every subsequent edit.
- *Adding new features*: new features are faster to add in a modular codebase, so modularization accelerates future feature work rather than competing with it.

** When to Split

A subsystem is ready for its own file when three things are true:

1. *Dense cluster.* Most of the content already lives in one place. A grep shows a tight concentration, not scattered crumbs across five files.
2. *Coherent boundary.* You can state the file's purpose in one sentence without saying "and also." =spellcheck.org= owns Flyspell, Jinx, Hunspell, and personal dictionaries — one subsystem. =org-workflow.org= would own "agenda and clocking and timeblocking and attach" — four subsystems, not one. That file should not exist yet.
3. *A reason you can name.* "Too big" is not a reason. "This subsystem is edited as a unit and would be easier to reason about in isolation" is a reason.

** The Test of Success

After each split, the next time you touch that subsystem, notice how much less friction there is. That felt difference — between "where does this live again?" and "open the file, change the thing" — is the payoff made concrete. If you do not feel it, the split was premature and something is still mislocated.

** Buffer-Local vs. Global State

*Design principle*: Keep state minimal and predictable.

*Buffer-local*:
- Major/minor modes
- Font-lock settings
- Temporary overlays

*Global*:
- Org-roam profile
- Custom functions
- Keybindings

*Ephemeral* (lost on restart):
- Window configuration
- Kill ring (clipboard history)
- Search history

* Technical Decisions and Rationale

** Why Spacemacs (Not Vanilla Emacs or Doom)?

*Pros*:
- Excellent layer system (curated package bundles)
- Great defaults
- Strong community
- Easy to extend

*Cons*:
- Slower startup than Doom or vanilla
- Some bloat from unused features
- Occasional version compatibility issues

*Decision*: Spacemacs' layer system and defaults are worth the tradeoffs for this use case (writing and note-taking focus).

** Why One Large shared-functions.org? (Historical — Decision Has Shifted)

This section documents a decision that has since been reversed. Keeping it for historical context and to record what changed.

*Original pros (as argued at the time)*:
- Single place to search for functions
- No dependency management between files
- Easy to see everything at once
- Simple to maintain

*Original cons*:
- Large file (~10,000 lines)
- Could be intimidating to newcomers
- Emacs handles it fine, but some tools might choke

*Original decision*: "For a personal config, convenience trumps modularity. Could split if working with a team."

*Current decision*: keep =shared-functions.org= as the home for genuinely general utilities, but extract a new =.org= file when a subsystem becomes both coherent and clearly out of place. [[file+emacs:/Users/jay/emacs/emacs-settings/org-authoring.org][org-authoring.org]] and [[file+emacs:/Users/jay/emacs/emacs-settings/spellcheck.org][spellcheck.org]] are the current examples of that targeted extraction pattern.

*Current decision*: Progressive extraction into focused modules is the preferred direction. See [[*Keep Modularizing][Keep Modularizing]]. The original "convenience" argument underestimated two forces that have grown in importance: accumulated file size (now ~10k lines) and the cost of loading large irrelevant context into AI assistants. The modularity argument was also framed as a team concern, but the payoffs (focused grep, tight AI context, physical refactor boundaries, coherent git history) all apply to a personal config too.

*Extraction track record*:
- =search-commands.org= — search/completion stack
- =fonts-and-themes.org= — UI/appearance + font/frame logic
- =spacecraft-mode.org= — prose editing helpers
- =org-authoring.org= — Org structure authoring
- =spellcheck.org= — spellchecking subsystem

** Why Literate Programming (Not Just .el Files)?

*Pros*:
- Documentation right with the code
- Easier to explain complex logic
- Great for learning and reference
- Beautiful exports to HTML/PDF

*Cons*:
- Extra step (tangle before use)
- Can get out of sync if you edit =.el= directly
- Requires discipline

*Decision*: Worth it for maintainability and understanding. The =#+auto_tangle: t= header helps.

** Why Separate Pasteboard Module?

*Pros*:
- Complex enough to deserve its own file
- Platform-specific (macOS only)
- Clear boundary for external dependencies
- Easier to test independently

*Cons*:
- One more file to track
- Requires loading separately

*Decision*: Clipboard cleaning is complex enough (~2,000 lines) and important enough (used constantly) to warrant separation.

** Why Org-Roam Profiles (Not Multiple Configs)?

*Pros*:
- Switch databases without restarting Emacs
- Shared functions and keybindings
- One codebase to maintain
- Clean separation of work/personal notes

*Cons*:
- Complexity in profile-switching code
- Need to remember which profile you're in

*Decision*: Much better than maintaining separate configs or mixing work/personal notes.

* Performance Considerations

** Startup Time

Current startup: ~5-8 seconds (depending on byte-compilation)

*Optimization strategies*:
1. Byte-compile all =.el= files → =.elc=
2. Defer loading non-essential packages
3. Lazy-load layers where possible
4. Minimize work in =dotspacemacs/user-config=

*To profile*:
#+BEGIN_SRC sh
emacs --timed-requires
#+END_SRC

** Memory Usage

*Large files*:
- =shared-functions.el=: ~316KB
- =spacemacs.d/init.el=: ~50KB
- =gnu-emacs-startup.el=: ~46KB

*Not a problem*: Emacs handles this fine. The byte-compiled versions load quickly.

** Byte Compilation

*Command*:
#+BEGIN_SRC emacs-lisp
(byte-recompile-directory "~/emacs/emacs-settings" 0)
#+END_SRC

*Benefits*:
- Faster function calls
- Faster startup
- Some error checking at compile time

*When to recompile*:
- After updating =.org= files and tangling
- After pulling from git
- If startup feels slow

* Extending the Configuration

** Adding a New Function

1. Choose location:
   - General utility → =shared-functions.org=
  - Clipboard-related → =pasteboard-copy-and-paste-functions.el=
   - Theme/appearance → =fonts-and-themes.org=

2. Add in a =#+BEGIN_SRC emacs-lisp= block

3. Document what it does

4. Tangle: =C-c C-v t=

5. Reload: =SPC f e R=

** Adding a New Module

1. Create =new-module.org= with =#+auto_tangle: t= header

2. Add to loading sequence in =spacemacs.d/init.el= or =gnu-emacs-startup.el=

3. Test loading order (make sure dependencies load first)

** Adding a Spacemacs Layer

1. Edit =spacemacs.d/init.el=

2. Find =dotspacemacs-configuration-layers=

3. Add layer name to list

4. =SPC f e R= to reload

5. Spacemacs will install packages on next restart

* Troubleshooting Architecture Issues

** Load Order Problems

*Symptom*: "void-variable" or "void-function" errors

*Cause*: Module A uses something from Module B, but B loads after A

*Solution*:
1. Find loading order in =spacemacs.d/init.el= or =gnu-emacs-startup.el=
2. Move Module B earlier
3. Or use =(require 'module-b)= at top of Module A

** Missing Dependencies

*Symptom*: "Cannot find file" or "Package not available"

*Solution*:
1. Check =dotspacemacs-additional-packages= in =spacemacs.d/init.el=
2. Check layer configuration
3. Try =SPC f e R= (reload) or =SPC f e U= (update packages)

** Tangle Sync Issues

*Symptom*: Changes in =.org= file not taking effect

*Cause*: Forgot to tangle, or Emacs loading old =.elc= file

*Solution*:
1. Delete =.elc=: =rm file.elc=
2. Tangle again: =C-c C-v t=
3. Reload: =SPC f e R=
4. Or restart Emacs

** Platform Issues

*Symptom*: Pasteboard functions not working on Linux

*Cause*: =pbcopy=/=pbpaste= are macOS-only

*Solution*:
- Linux: Modify to use =xclip= or =xsel=
- Windows: Use PowerShell clipboard commands
- Or wrap in =(when (eq system-type 'darwin) ...)=

* Architecture Principles

** Design Philosophy

1. *Modularize by subsystem*: File-per-subsystem when the boundary is coherent. See [[*Keep Modularizing][Keep Modularizing]] for the full rationale.
2. *Pragmatism over dogma*: Choose the structure that makes the next edit easier. Don't split where the boundary isn't real; don't keep a monolith once the boundary becomes obvious.
3. *Documentation is code*: Literate programming keeps them in sync
4. *Adapt to context*: Smart functions beat mode-specific commands
5. *Integration matters*: Deep macOS integration enhances workflow
6. *Stable core, flexible edges*: Spacemacs base, custom extensions

** Maintenance Philosophy

1. *Git everything*: Commit often, with good messages
2. *Document surprises*: Non-obvious fixes go in =codebase-wisdom.org=
3. *Test before pushing*: Use git branches for experiments
4. *Keep it working*: Functionality over elegance
5. *Fix forward*: Deprecation warnings are technical debt

** Future Considerations

See =critical-next-steps.org= for planned improvements, but key architectural goals:

1. Better error handling (graceful degradation)
2. More consistent naming conventions
3. Cleaner dependency management
4. Continue extracting coherent subsystems from =shared-functions.org= when they meet the criteria in [[*Keep Modularizing][Keep Modularizing]].
5. Consider use-package for cleaner package configuration

* Core Philosophy (Condensed)

** Writing First, Coding Second
This is primarily a *writing environment*, not a development environment. Typography matters, clipboard integration is crucial, org-mode is central.

** Literate Programming
Code and documentation live together. Future-you needs to understand past-you's decisions.

** macOS Integration
Deep platform integration (pbcopy/pbpaste, Command key) enhances workflow. Tradeoff: less portable, but much more useful on primary platform.

** Org-Mode Centrality
Org-mode is the canonical format for everything: notes, tasks, documentation, code, journal entries.

** Pragmatism Over Dogma
Choose the structure that makes the next edit easier — not the one that matches an abstract ideal. Focused modular files when the subsystem boundary is coherent (see [[*Keep Modularizing][Keep Modularizing]]); a single file when splitting would invent false boundaries. Some copy-pasted code when abstraction is harder to read than repetition. "Good enough" beats "perfect but unfinished."

** Adaptive Behavior
Functions detect context and do the right thing. =pasteboard-paste-adaptive= cleans in org buffers, pastes raw in code. Fewer commands to remember.
