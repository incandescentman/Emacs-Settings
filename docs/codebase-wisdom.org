* Hipster CV Needs FontAwesome Seeded Before =\documentclass= Under XeLaTeX
  Date: 2026-05-31

** Trigger
The active LaTeX template audit found that [[file+emacs:/Users/jay/emacs/emacs-settings/latex-templates/hipster-cv.el][hipster-cv.el]] failed under XeLaTeX with =Package fontspec Error: The font "FontAwesome" cannot be found=, even though =kpsewhich FontAwesome.otf= found TeX Live's bundled OTF at [[file+emacs:/usr/local/texlive/2025/texmf-dist/fonts/opentype/public/fontawesome/FontAwesome.otf][FontAwesome.otf]].

** Mechanism
The local =simplehipstercv= class loads =simplehipstercv.sty= during =\documentclass=, and that style loads the old =fontawesome= package immediately. Because =fontawesome.sty= hardcodes =\newfontfamily{\FA}{FontAwesome}=, adding fontspec defaults after =\documentclass= is too late: the package has already tried and failed to resolve the font family. LuaLaTeX can find the TeX Live font in this setup, but the repo's Org PDF export path is XeLaTeX-oriented.

** Actionable insight
- For =hipster-cv=, seed FontAwesome before =\documentclass= with =\RequirePackage{fontspec}= plus =\defaultfontfeatures[FontAwesome]{Path = /usr/local/texlive/2025/texmf-dist/fonts/opentype/public/fontawesome/, Extension = .otf}=.
- If this breaks after a TeX Live year bump, re-run =kpsewhich FontAwesome.otf= and update the path in [[file+emacs:/Users/jay/emacs/emacs-settings/latex-templates/hipster-cv.el][hipster-cv.el]] rather than patching [[file+emacs:/Users/jay/Library/texmf/tex/latex/simplehipstercv/simplehipstercv.sty][simplehipstercv.sty]].

* Guard =org-attach-attach= Directly When Preventing Attachment Accidents
  Date: 2026-05-26

** Trigger
Trying to attach one SVG from a Roam note accidentally copied a whole =Downloads/= directory into /Users/jay/Dropbox/roam/attachments/, creating a 7.6 GB untracked attachment tree.

** Mechanism
Org's =org-attach-attach= accepts both files and directories. When given a directory and method =cp=, it normalizes the trailing slash and calls =copy-directory= into the attachment directory. Guarding only the top-level =org-attach= menu would miss programmatic callers and helper packages that call =org-attach-attach= directly.

** Actionable insight
- Put safety checks around =org-attach-attach= itself when blocking dangerous attachment inputs.
- Reject directories before calling the original function; normal file attaches should pass through unchanged.
- If the accident starts with picker friction, improve the interactive spec too. In this config, the attach prompt should present regular non-hidden files from /Users/jay/Downloads/ in newest-added-first order, while the lower-level guard remains as the final backstop.
- Do not rely on =read-file-name='s =DEFAULT-FILENAME= in Jay's compleseus/Vertico setup. Vertico's RET path exits with the highlighted candidate, and its default sorting is history/length/alpha rather than file recency. For ordered file pickers, use a custom completion table whose metadata declares =display-sort-function= and =cycle-sort-function= as =identity=.
- If a custom picker narrows the normal file-navigation surface, include an explicit escape-hatch candidate that calls =read-file-name= so arbitrary existing files remain attachable.
- For future attachment failures, check both the Org note link and the attachment tree. A directory-shaped attachment can be large, untracked, and unreferenced.

* Keep =num:t= When A LaTeX TOC Needs Unnumbered Headings
  Date: 2026-05-25

** Trigger
In [[file+emacs:/Users/jay/Dropbox/roam/events/jay-birthday-2026/20260522233127-tarot_deck.org][Jay Birthday Tarot Deck Questions]], changing the export options from =num:t= to =num:nil= looked like the cleaner way to produce unnumbered section headings. The PDF still emitted =\tableofcontents=, but the table of contents came out empty.

** Mechanism
For LaTeX export, Org's =num:nil= does more than hide printed section numbers. It changes exported headings from normal sectioning commands to starred commands:

#+begin_src latex
\section*{Tarot Deck}
\subsection*{THE JAY-CHARACTER CARDS}
#+end_src

Starred LaTeX section commands do not write entries to the =.toc= file by default. So =toc:t= can still emit =\tableofcontents=, but there is nothing for LaTeX to list.

The older snippet pattern is intentional:

#+begin_src org
#+OPTIONS: H:5 num:t toc:t
#+LATEX_HEADER: \setcounter{secnumdepth}{0}
#+LATEX_HEADER: \setcounter{tocdepth}{3}
#+end_src

With =num:t=, Org emits normal =\section{...}= and =\subsection{...}= commands, which populate the table of contents. The LaTeX =secnumdepth= setting then suppresses visible printed numbers. This is not stale boilerplate; it separates TOC participation from number display.

** Actionable insight
- If a LaTeX export needs a table of contents with unnumbered-looking headings, keep =num:t= and use =\setcounter{secnumdepth}{0}=.
- Do not "simplify" that pair to =num:nil= unless you also add explicit =\addcontentsline= handling or otherwise customize the exporter.
- Fast diagnostic: inspect the generated =.tex=. If headings are =\section*= / =\subsection*= and the TOC is empty, the problem is section-star export, not the LaTeX class.

* "Fallback" Coercion Loops Must Respect The Same Heuristic As The Primary
  Date: 2026-05-19

** Trigger
=pasteboard-paste-adaptive= rewrote top-level =* Heading= lines to =- Heading= when the same clipboard text also contained any =-= bullets. The repro was a Claude reply that used =* Option 1 / * Option 2 / * Option 3 / * My pick= section headings plus a small =- a / - b / - c= "three reasons" list inside one of those sections. Every =* Option N= turned into =- Option N= on paste.

** Mechanism
Two bugs compounded inside [[file+emacs:/Users/jay/emacs/emacs-settings/pasteboard-copy-and-paste-functions.el][pasteboard-copy-and-paste-functions.el]]:

1. =pasteboard--analyse-clipboard-text= only scored =\\*\\{2,\\}= (two-or-more-star) lines as Org headings. Single-star Org headings contributed *zero* to =org-score=, so any text that mixed single-star Org headings with =-= bullets always tipped =md-score >= org-score + 2= and the analyser chose =style = 'markdown=.

2. The primary converter, =pasteboard--convert-asterisk-bullets-to-dashes=, was actually *correct*: it called =pasteboard--should-convert-asterisk-line= per match, and that helper would leave a top-level =* = line alone when its non-blank neighbors were plain paragraph text (heading-like) rather than other list items. But =pasteboard--clean-string= contained a "fallback" loop right after the primary that *unconditionally* rewrote every remaining =^\\* = line to =- =:

   #+begin_src elisp
   ;; Fallback: if any single-asterisk lines slipped through, coerce them now.
   (while (re-search-forward "^\\([ \t]*\\)\\* \\(.*\\)$" region-end t)
     (let ((line-no (line-number-at-pos (match-beginning 0))))
       (unless (and skip-lines (memq line-no skip-lines))
         (replace-match "\\1- \\2" t))))
   #+end_src

   The fallback's =skip-lines= protected only lines that had been recognized as =##=-style Markdown headings up front. Single-star Org headings were not on that list, so the fallback silently undid every protection the primary converter had carefully applied.

The first bug alone would have been recoverable — the primary converter still made the right call on each =* = line. It was the second bug that turned the misclassification into actual data corruption.

** The Fix
Two targeted edits in [[file+emacs:/Users/jay/emacs/emacs-settings/pasteboard-copy-and-paste-functions.el][pasteboard-copy-and-paste-functions.el]]:

1. =pasteboard--analyse-clipboard-text= now classifies every top-level single-=*= line by its non-blank neighbors via =pasteboard--neighbor-nonblank-kind=. Indented or list-neighbored lines still count as =asterisk-bullets= (bullet-like); lines surrounded by paragraph text or other Org headings score =org-score += 1= (heading-like).

2. The fallback loop in =pasteboard--clean-string= now calls =pasteboard--should-convert-asterisk-line= per match — the same heuristic the primary converter uses. Heading-like top-level =* = lines are preserved even if the analyser still picks =style = 'markdown= upstream.

Verified against the repro text under =emacs --batch=: analyser now reports =style = nil= (was =markdown=), and all four =* Option N / * My pick= headings survive the clean pipeline. Pure =* Apple / * Banana / * Cherry= bullet lists still classify as Markdown via the unchanged =asterisk-bullets >= 3= rule in the cascade.

** Actionable insight
- *Symptom signature*: a heuristic-aware function appears to do the right thing in isolation, but its caller still produces the wrong output. Suspect a downstream "defense-in-depth" pass that does *not* consult the same heuristic.
- *Anti-pattern to recognize when reading code*: a comment like "Fallback: if any X slipped through, coerce them now" followed by an unconditional rewrite. If the primary path was conditional, the fallback must be conditional too — otherwise the fallback is not defense in depth, it is a silent override.
- *Rule for adding belt-and-suspenders cleanup*: the belt and the suspenders must agree on what they are holding up. If the primary converter consults =pasteboard--should-convert-asterisk-line=, every later sweep that touches the same lines must consult it as well.
- *Detection-vs-action separation*: when a detector (=pasteboard--analyse-clipboard-text=) feeds an action (=pasteboard--clean-string=), be skeptical of action-level fallbacks that operate on signals the detector classified ambiguously. They re-introduce the very ambiguity the detector tried to resolve.
- *Debugging path that would have found this faster*: when an unwanted transformation happens, =M-x trace-function= the primary converter — if it shows the line being *skipped*, the corruption is happening somewhere downstream of it, not inside it. The bug is in whatever runs after.
- *Dynamic replacement rule*: if =replace-match= receives text assembled from clipboard or buffer content, pass non-nil =FIXEDCASE= and =LITERAL= arguments unless backreference expansion is intentionally required. Otherwise an ordinary user backslash such as =\EnableLogoFooter= is parsed as replacement syntax and raises =Invalid use of ‘\’ in replacement text=.
  Date: 2026-05-15

** Trigger
While building [[file+emacs:/Users/jay/emacs/emacs-settings/assets/css/new-yorker.css][assets/css/new-yorker.css]] (the HTML/Prince companion to the New Yorker LaTeX class), heading text and the byline rendered as ALL CAPS in Chrome and in Prince PDF output, even though no =text-transform: uppercase= or =font-variant: small-caps= rule was in effect. Removing the explicit small-caps rule did not fix it.

** Mechanism
The font cascade started with =font-family: Irvin, "Playfair Display", "Bodoni 72", "Bodoni 72 Smallcaps", Didot, ...=. Two of those entries silently force uppercase rendering by the *font itself*, not by any CSS transform:
- *Irvin* (the New Yorker's iconic display face, installed locally so the LaTeX template can use it) is a titling font containing only uppercase glyphs. When the browser asks it to render lowercase letters, it substitutes the uppercase form because no lowercase form exists in the font file.
- *Bodoni 72 Smallcaps* (a default macOS font) has the smallcaps treatment baked into its glyph table — every "lowercase" character is already a smallcap.

So if Irvin (or Bodoni 72 Smallcaps) is installed and is the first matching family in the cascade, the browser uses it and you get all-caps with zero CSS hint that anything is wrong. =text-transform=, =font-variant=, and =font-feature-settings= will all show "none" / "normal" in DevTools.

** The Fix
Scope uppercase-only display faces to the elements where all-caps is intended (the article title / =h1=). For headings and bylines that should read in mixed case, either:
1. Drop the offending font from the cascade entirely, or
2. Use a different cascade for those elements (e.g., the body serif at a larger size).

In =new-yorker.css= this means =h1= keeps the Irvin cascade, while =h2-h6= and =.byline= use a Caslon body cascade or a sans-serif (Neutraface analogue) cascade that contains real mixed-case glyphs.

** Actionable insight
- *Symptom signature to recognize next time*: text rendering as ALL CAPS in HTML output despite no =text-transform= / =font-variant= rule. First diagnostic in DevTools: inspect the element's *Computed* font-family — whichever family the browser actually picked is the culprit.
- *Display fonts to suspect on macOS*: any titling face (Irvin, old Trajan-style fonts, single-case display fonts), and the explicit "Smallcaps" family variants (Bodoni 72 Smallcaps, etc.). These are not browser bugs — the fonts genuinely lack the missing glyphs.
- *Rule of thumb when adding a font to a CSS cascade*: if the font name includes "Smallcaps", "Titling", "Display", or "Caps", confirm it has lowercase glyphs before placing it ahead of mixed-case fonts in the fallback chain.
- *Translation gotcha when porting LaTeX templates to CSS*: LaTeX classes can use uppercase-only display faces for section headings because LaTeX users typically intend that effect. CSS gets the same all-caps result for free, but only at heading levels where you actually want it — scope the display face to those levels.

* =(buffer-file-name)= Returns Nil In Indirect Buffers
  Date: 2026-05-15

** Trigger
=path-copy-path-to-clipboard= (bound to =s-|=) appeared to silently do nothing when invoked from inside an indirect buffer — no message, no clipboard update — even though it worked fine in the underlying file buffer.

** Mechanism
Indirect buffers (created by =clone-indirect-buffer=, =org-tree-to-indirect-buffer=, =C-x 4 c=, etc.) share text with a base buffer but are *not themselves visiting a file*. =(buffer-file-name)= consults the buffer-local =buffer-file-name= variable on the current buffer, which is nil for indirect buffers — only the base buffer holds the file path. Any function that gates behavior on =(when filename ...)= silently no-ops.

** The Fix
Use =(buffer-file-name (buffer-base-buffer))= instead of bare =(buffer-file-name)=. =(buffer-base-buffer)= returns the base buffer of an indirect buffer, or nil if the current buffer is not indirect. When passed nil, =buffer-file-name= falls back to the current buffer — so the substitution is a strict superset of the original behavior and doesn't need a conditional.

Applied in [[file+emacs:/Users/jay/emacs/emacs-settings/shared-functions.org][shared-functions.org]] for both =path-copy-path-to-clipboard= and =path-copy-path-to-clipboard-with-quotes=.

** Actionable insight
- Any utility that reads =(buffer-file-name)= and is callable from prose-editing contexts (Org subtree narrowing via indirect buffers, =org-edit-special= source blocks, etc.) should prefer =(buffer-file-name (buffer-base-buffer))=.
- Same gotcha applies to =default-directory= consumers if the indirect buffer was created with a different =default-directory= than its base — but that's much rarer.
- Symptom signature to recognize next time: a path/file-aware command works in some buffers and silently does nothing in others, with no error and no message. First diagnostic: =M-: (buffer-file-name)= in the failing buffer; if it returns nil, check =(buffer-base-buffer)=.

* Contract Signature Blanks In Org LaTeX Should Be Real Rules, Not Underscore Runs
  Date: 2026-05-05

** Trigger
In [[file+emacs:/Users/jay/emacs/emacs-settings/metabolic-mind-contract-1.org][metabolic-mind-contract-1.org]], signature and date blanks were written as long underscore runs:

#+begin_src org
Signature: ________________________________
Date: ____________________________________
#+end_src

Those exported weirdly in PDF because this config's Org→LaTeX stack treats underscores as underline markup rather than as inert blank lines.

** Mechanism
The export behavior is not accidental. [[file+emacs:/Users/jay/emacs/emacs-settings/org-export.org][org-export.org]] explicitly maps underscore emphasis to LaTeX underline commands:

#+begin_src emacs-lisp
("_" "\\underline{%s}" nil)
#+end_src

and also routes underline text markup through =\uline{...}=. So a row of underscores in contract signature blocks is the wrong primitive for "blank line" in this repo's LaTeX exports.

** The Fix
For future contracts, the clearest explicit source form is still an Org macro that emits a literal LaTeX rule:

#+begin_src org
#+MACRO: sigline @@latex:\rule{2.75in}{0.4pt}@@
#+end_src

Then use it like:

#+begin_src org
Signature: {{{sigline}}}
Date: {{{sigline}}}
#+end_src

For more complex contract layouts (signature + date columns, multiple signers, etc.), use a small =#+begin_export latex= block with =tabular= or =minipage= rather than trying to compose the geometry out of punctuation characters.

This repo now also has a narrow export safety net in [[file+emacs:/Users/jay/emacs/emacs-settings/org-export.org][org-export.org]]: during *LaTeX export only*, if an Org file is tagged =:contract:= and contains simple lines like:

#+begin_src org
Signature: ________________________________
Date: ____________________________________
#+end_src

the export preprocessor rewrites just those lines into literal =\rule{...}= blanks in the temporary export buffer. That means future contracts can still export cleanly even if the source uses underscore blanks by habit.

** Actionable insight
For future Codex sessions working on contracts in this repo:

- Prefer a file-local =sigline= macro for ordinary contracts; it keeps the source explicit and portable.
- If a contract Org file is tagged =:contract:=, this repo's LaTeX export path will automatically repair simple =Signature:= / =Date:= underscore blanks into real rules.
- If the layout is more complex than one line per signer, use explicit LaTeX export blocks.
- Do *not* "fix" this by changing global underscore export behavior in [[file+emacs:/Users/jay/emacs/emacs-settings/org-export.org][org-export.org]] unless there is a repo-wide decision to change underline semantics everywhere.

* =key-minor-mode-map= Wins Over Major-Mode Keymaps — Use =minor-mode-overriding-map-alist= For Per-Mode Overrides
  Date: 2026-05-03

** Trigger
Adding =s-p= → =jay/fountain-export-and-open= to =my/fountain-mode-bindings= in [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]], and installing it into =fountain-mode-map= via =my/install-mode-bindings=, did nothing visible. Pressing =s-p= in a Fountain buffer still ran =org-export-dispatch=. The binding was structurally correct — it just lost the precedence battle.

** Mechanism
This config wraps a near-global keymap, =key-minor-mode-map=, in the =key-minor-mode= minor mode (defined at the top of [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]]) and installs =my/global-key-bindings= into it. Among those is =("s-p" . org-export-dispatch)=. Emacs's keymap precedence rule is unambiguous: minor-mode keymaps (resolved through =minor-mode-map-alist=) win over major-mode keymaps. A binding installed into =fountain-mode-map= for any key already in =key-minor-mode-map= is therefore dead — the major map never gets the lookup.

This isn't a Fountain-specific problem. It applies to *every* major mode in this config. The reason it doesn't bite more often is that most mode-specific bindings happen to use keys that aren't already in =key-minor-mode-map=. Anytime you want a major mode to *override* a globally-bound key, the major map is the wrong place to put it.

The same trap is already documented inline at [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]]'s =my/vertico-override-bindings= comment (lines ~691–695): /"These must go in =vertico-map= (not =key-minor-mode-map=) because =key-minor-mode= is intentionally disabled inside the minibuffer..."/ — a different precedence puzzle, but the same family.

** The Fix
Use =minor-mode-overriding-map-alist=, which is a per-buffer override mechanism that Emacs explicitly designs into =key-lookup= for exactly this case. Hook a function onto the major mode that builds a small keymap parented to =key-minor-mode-map= (so unaffected keys still resolve normally), defines the conflict-keys, and installs it via =minor-mode-overriding-map-alist=. The override is buffer-local, so it doesn't leak to non-Fountain buffers.

The current implementation lives in [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]] as =my/fountain-install-key-minor-overrides= and is hooked from =fountain-mode-hook= inside the =with-eval-after-load 'fountain-mode= block. The pattern generalizes — any future major-mode override of a =key-minor-mode-map= binding should follow the same shape.

** Actionable insight
*Symptom:* "I added a binding to =my/<MODE>-mode-bindings= and =my/install-mode-bindings= installed it correctly, but pressing the key still runs the global command." → The key collides with =my/global-key-bindings= and the major-mode binding is shadowed. =describe-key= will report the global command. The fix is *not* to change install order, define-key into a different map, or adjust load timing — it's to use =minor-mode-overriding-map-alist= via a buffer-local hook on the mode.

*Don't:* set =key-minor-mode= to nil in the mode-hook (kills every other global binding), or rely on =local-set-key= (modifies the major-mode map, which still loses the precedence battle).

** Trigger
=jay/fountain-export-and-open= in [[file+emacs:/Users/jay/emacs/emacs-settings/gnu-emacs-startup.org][gnu-emacs-startup.org]] built a sentinel lambda that referenced =pdf= from the surrounding =let*=. The first invocation produced =Debugger entered--Lisp error: (void-variable pdf)= when the sentinel fired, even though =pdf= was clearly bound when the lambda was constructed.

** Mechanism
[[file+emacs:/Users/jay/emacs/emacs-settings/gnu-emacs-startup.el][gnu-emacs-startup.el]] (the tangled output) does not have a =;;; -*- lexical-binding: t -*-= file header, so it loads under dynamic binding. Under dynamic binding, a lambda is *not* a closure — it does not capture surrounding variable bindings. When =let*= unwinds at the end of the function call, the =pdf= binding is gone. The lambda then runs later (when the async process exits) with no =pdf= in scope, and dies with =void-variable=.

This is not specific to sentinels — anywhere a lambda escapes its lexical scope (timer callbacks, hooks, advice functions, after-change-functions) the same trap applies in dynamically-bound files.

** The Fix
Two viable options. The current code uses option (1):

1. *Pass state via process properties.* =process-put= attaches data to the process object before installing the sentinel; =process-get= retrieves it inside the sentinel. The process object itself is the argument to the sentinel and is always live, so this works regardless of binding mode:
   #+begin_src emacs-lisp
   (process-put proc 'fountain-pdf pdf)
   (set-process-sentinel
    proc
    (lambda (p _event)
      (let ((out (process-get p 'fountain-pdf)))
        ...)))
   #+end_src

2. *Add the lexical-binding header to the file.* Cleaner long-term, but for tangled =.org= → =.el= files you have to add it via a =:tangle= header argument or an =#+begin_src emacs-lisp= block that emits the cookie. Touching the file header has wider implications (other code in the same file might rely on dynamic binding), so option (1) is the localized fix.

** Actionable insight
*Symptom:* Async callback in a =gnu-emacs-startup.org= / =shared-functions.org= / any other tangled or non-lexical Elisp file complains about a void variable that you can clearly see in the surrounding =let*= or =defun= arglist. → It's not a typo. The lambda escaped its scope and the binding unwound.

*Quick triage:* check =(elt (assq 'lexical-binding file-local-variables-alist) 1)= in the file's buffer, or look at the first line for the =-*- lexical-binding: t -*-= cookie. If absent and the lambda is async, refactor to =process-put= / =process-get= or a similarly explicit data-passing channel. Don't reach for =lexical-let= — it's been deprecated since Emacs 24.

* Three Ways To Get LaTeX Token-Register Emptiness Tests Wrong
  Date: 2026-04-20

** Trigger
The Elegant Garamond LaTeX templates were supposed to fall back to =\@title= when =\leftheader{...}= was omitted. The left header stayed blank. Fixing it took three iterations because each naive fix stumbled into a different LaTeX expansion trap.

** Mechanism — the three traps

*** Trap 1: =\ifstrempty{\the\reg}= ignores the register
=etoolbox='s =\ifstrempty{<arg>}{<true>}{<false>}= applies =\detokenize= to =<arg>= *without expanding it first*. So =\ifstrempty{\the\leftheader}{...}{...}= detokenizes to the literal string =\the\leftheader=, which is never empty. The true branch cannot fire.

*** Trap 2: =\edef\tmp{\@title}= crashes on fragile titles
Switching to =\edef\tmp{\the\reg}= / =\ifx\tmp\@empty= fixes the test, but if the fallback branch is =\edef\jayresolvedleftheader{\@title}=, =\edef= force-expands =\@title=. Org =\title{...}= often contains fragile content (raw =#=, =\\=, =\medskip=, =\large=, unexpanded macros, subtitle concatenation), which crashes with =Illegal parameter number= or =Undefined control sequence= at =\begin{document}=.

*** Trap 3: =\def\tmp{\the\reg}= makes =\ifx ...\@empty= always false
Swapping =\edef= for =\def= to avoid the crash creates a new bug: =\def\tmp{\the\reg}= sets =\tmp='s replacement text to the literal two tokens =\the\reg=, which is not =\ifx=-equal to =\@empty=. The emptiness test always takes the false branch, the fallback never fires, and the header silently renders blank again.

** Safe pattern

Use =\expandafter= to force =\the= to expand before =\ifstrempty= sees the argument, and use =\let= (or delimited-argument splitting) instead of =\edef= on the content:

#+begin_src latex
\expandafter\ifstrempty\expandafter{\the\leftheader}
  {\let\jayresolvedleftheader\@title}
  {\def\jayresolvedleftheader{\the\leftheader}}%
#+end_src

For Org documents specifically, =\@title= concatenates =#+SUBTITLE:= as =<title>\\\medskip\large <subtitle>=, so taking =\@title= whole drags the subtitle into the header. Split at the first =\\= with a delimited macro:

#+begin_src latex
\def\jay@leftheader@split#1\\#2\jay@leftheader@end{\def\jayresolvedleftheader{#1}}
...
{\expandafter\jay@leftheader@split\@title\\\jay@leftheader@end}
#+end_src

Appending =\\\jay@leftheader@end= makes the pattern match even when the title contains no =\\=.

** Actionable insights
- =\ifstrempty= tests *tokens*, not *expansions*. Force a single level of expansion with =\expandafter\ifstrempty\expandafter{\the\reg}=.
- Never =\edef= =\@title= or any Org-emitted macro — treat them as fragile. Use =\let= or delimited-argument copying to preserve tokens.
- =\def\x{\the\reg}= does not test emptiness — it stores a recipe. =\ifx\x\@empty= against such a macro is always false.
- For Org LaTeX exports, =\title{...}= includes the subtitle inline. If you want the title only, split at =\\=.
- Before declaring a LaTeX fix resolved, test against a real project file, not just a synthetic minimal repro — titles with fragile content and subtitles are what actually break these paths.

** The Bug
When selecting all text in a buffer and calling `my/delete-backward-and-capitalize`, the function would fail to delete the highlighted region correctly.

** The Truth

#+BEGIN_SRC emacs-lisp
(let* ((has-region (use-region-p))

       (region-end (when has-region (region-end)))
       ...)

* TeX Hyphenation Knobs: Theoretical Clean Can Lose to Empirical Badness
  Date: 2026-04-23

** Trigger
A bullet in [[file+emacs:/Users/jay/Dropbox/roam/storytelling-nyc-roam/20260422-xia-luu-baszucki-proposal.org][20260422-xia-luu-baszucki-proposal.org]] rendered with a "runt": ~ses-~ on line 1, ~sion.~ stranded alone on line 2. Over a long thread, two theoretical fixes were tried, committed, and tested — and both visibly failed in the exported PDF even though they were applied correctly at the preamble.

Attempts in order:
1. =\hyphenpenalty=10000= + =\righthyphenmin=4= + =\setlist{before=\RaggedRight}=. Blunt but working. Codex critiqued as over-aggressive, and the =\RaggedRight= in lists (=ragged2e=) doesn't actually prevent list hyphenation the way Claude's commit message implied — =\RaggedRight= has a finite =\RaggedRightRightskip= of ~2em and still permits hyphenation under pressure.
2. Swap to =\finalhyphendemerits=1000000= + =\setlist{before=\RaggedRight}=. Codex's theoretically cleaner fix, targeting the exact penultimate-line-hyphenation pattern.
3. Drop =\setlist{before=\RaggedRight}= after Jay disliked the ragged-bullet texture, leaving =\finalhyphendemerits=1000000= alone. Jay re-exported — *same runt*.

** Mechanism
=\finalhyphendemerits= adds a per-break demerit when the penultimate line is hyphenated and the next line is the paragraph's last. In principle that's exactly this failure. In practice, TeX's line-break algorithm picks the line-break set with the minimum total demerits, and each break contributes =(\linepenalty + \badness)² + penalty_demerits=.

In Garamond Premier Pro at 12pt with =\setstretch{1.2}= and a narrow enumitem measure, the non-hyphenated alternative breakpoints for that specific bullet produce loose line 1s with badness values where =badness²= dominates — often 25M+ demerits per alternative. =\finalhyphendemerits=1000000= contributes only 1M to the hyphen-ending break. So TeX still picks the hyphen. The theory is right; the arithmetic just doesn't favor =\finalhyphendemerits= in this preamble.

Diagnostic that settled it: an empirical knob matrix run against the actual document with the real class preamble. Tested knobs A–I; only =\hyphenpenalty=10000=, =\righthyphenmin=5=, =\pretolerance=10000=, and =\hyphenation{session}= actually eliminated the runt. =\finalhyphendemerits=1000000=, =\hyphenpenalty=5000=, =\finalhyphendemerits= + =\hyphenpenalty=5000=, =\righthyphenmin=4=, and =\doublehyphendemerits= all failed.

The adopted fix: =\righthyphenmin=5= in [[file+emacs:/Users/jay/emacs/emacs-settings/latex-templates/jay-latex-prose-defaults.el][latex-templates/jay-latex-prose-defaults.el]]. It refuses hyphenation whenever the tail landing on the next line would be ≤4 characters — which covers the ugly runt cases — and leaves long-tail hyphenation untouched.

** Fast-test protocol
Before recommending a hyphenation knob for a specific failure, run this against the real document:

#+begin_src sh
cp /path/to/user-source.org /tmp/runt.org
emacs --batch \
  --eval "(require 'ox-latex)" \
  --eval "(load \"/Users/jay/emacs/emacs-settings/latex-templates/elegant-garamond.el\" nil 'nomessage)" \
  --eval "(find-file \"/tmp/runt.org\")" \
  --eval "(org-latex-export-to-latex)"
cd /tmp && xelatex -interaction=nonstopmode runt.tex >/dev/null 2>&1 && \
             xelatex -interaction=nonstopmode runt.tex >/dev/null 2>&1
pdftotext -layout /tmp/runt.pdf - | grep -A2 "target phrase"
#+end_src

This is fast (~5s per iteration) and rules out both cache-staleness and theoretical misfires.

** Actionable insights
- TeX hyphenation fixes must be *tested empirically against the real preamble*. The demerit arithmetic depends on font metrics, measure, and line stretch — theoretical knobs that "should" work often don't, because alternative-break badness (=badness²=) outstrips modest per-break penalties.
- =\finalhyphendemerits= is not a reliable anti-runt fix in Garamond + tight enumitem measures. Don't reach for it first for this codebase's prose classes.
- =\righthyphenmin=N= is the narrowest knob that actually fixes short-tail runts. Each bump up the scale (=3= → =4= → =5=) forbids more hyphenations whose tails would be shorter than =N=. The default is =3= for English; this codebase uses =5= in prose defaults.
- =\RaggedRight= from =ragged2e= is *not* a no-hyphenation command — it still permits hyphenation under pressure (finite =\RaggedRightRightskip=). Only standard =\raggedright= eliminates hyphenation by giving =\rightskip= infinite stretch.
- When an AI collaborator (Codex, Claude, whatever) recommends a theoretical TeX knob confidently, run the empirical test matrix before adopting. Confident theoretical wrong answers are expensive to unwind — three commits this session tried knobs that didn't work.
