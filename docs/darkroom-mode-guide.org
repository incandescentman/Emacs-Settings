#+title: Darkroom Mode Guide

* What Darkroom is

Darkroom is a writing-focused minor mode from João Távora. In package terms, it is more aggressive than Olivetti.

- It centers the text by setting window margins.
- It hides the mode line and header line while active.
- It can enlarge the text.
- It has a special split-aware mode, =darkroom-tentative-mode=, that only enters full Darkroom when the buffer is the sole window in the frame.

Current behavior:

- Darkroom margins are not using the package's default guessing function. This config overrides them with =jay/darkroom-fixed-width-margins=.
- The current target body width is controlled by =jay/darkroom-body-width= and defaults to =80= columns.

- =poet-mode= turns on plain =darkroom-mode= directly, not tentative mode.

So the live behavior in this repo is:

- centered writing column
- hidden mode line and header line while Darkroom is actually active
- automatic enter/exit on splits for the writing modes above
- no automatic text enlargement unless you change the setting

* What tentative mode does

=darkroom-tentative-mode= is the most distinctive part of Darkroom.

- If the current buffer is the only window in the frame, it enters full =darkroom-mode=.
- If you split windows, it leaves full =darkroom-mode=.
- If you go back to a single window, it re-enters full =darkroom-mode=.

That means it acts like: "focus mode when writing alone, normal mode when working side by side."

This is the main behavioral difference from Olivetti in practice. Olivetti centers text, but it does not have this split-aware "only when solo" behavior built in.

* How to use it in this config

The easiest way to test the current setup is to open an Org or text buffer and use the bindings already wired in [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]]:

- =s-k o l= toggles Darkroom for the current buffer.
- =] ol= is another toggle for the current buffer.
- =s-k o e= widens the margins.
- =s-_= narrows the margins.

Important nuance about the toggle:

- If you toggle from a single-window frame, the wrapper prefers =darkroom-tentative-mode=.
- If you toggle from a multi-window frame, the wrapper enables plain =darkroom-mode= in the current buffer instead.
- If Darkroom is already active, the toggle turns it off.

Direct commands worth trying:

#+begin_src text
M-x darkroom-mode
M-x darkroom-tentative-mode
M-x customize-group RET darkroom RET
#+end_src

The distinction matters:

- Use =darkroom-mode= if you want Darkroom to stay on even when the frame is split.
- Use =darkroom-tentative-mode= if you only want it while writing in a single window.

* What Darkroom actually hides

"Chrome" here means editor UI around the text, not the Google Chrome browser.

Darkroom itself explicitly saves and hides:

- the mode line
- the header line
- fringe placement behavior

It also adjusts window margins.

Darkroom does /not/ automatically manage everything you might mentally classify as "UI chrome." For example, in the package source it does not directly toggle line numbers. If you want line numbers off while writing, that would need to be a separate config choice.

* Options worth experimenting with

The package-level options most worth testing are:

** =darkroom-text-scale-increase=

Package default: =2=

Current config: =0=

What it does:

- Controls how much text size increases when full =darkroom-mode= activates.

Why test it:

- Right now you are only testing Darkroom as "centered text plus hidden chrome."
- If part of the appeal is a bigger, more immersive writing surface, try turning this back on.

Try:

#+begin_src emacs-lisp
(setq darkroom-text-scale-increase 1)
#+end_src

or

#+begin_src emacs-lisp
(setq darkroom-text-scale-increase 2)
#+end_src

One caveat from the package source: Darkroom leaves by calling =text-scale-mode -1=. So if you rely on pre-existing per-buffer text scaling, experimenting with text enlargement is worth doing with that in mind.

** =darkroom-margins=

Package default: =darkroom-guess-margins=

Current config: =#'jay/darkroom-fixed-width-margins=

What it does:

- Controls how Darkroom computes left and right margins.

It can be:

- a float such as =0.18=, meaning percentage-of-window margins
- a cons cell such as =(20 . 20)=, meaning fixed left/right margins in columns
- a function, which is what this repo currently uses

Why test it:

- If the current fixed-width feel is too rigid, percentage margins can feel looser.
- If you want package-native behavior, you can try the guessing function.

Try:

#+begin_src emacs-lisp
(setq darkroom-margins 0.18)
#+end_src

or

#+begin_src emacs-lisp
(setq darkroom-margins '(20 . 20))
#+end_src

or

#+begin_src emacs-lisp
(setq darkroom-margins #'darkroom-guess-margins)
#+end_src

Important caveat from the package source:

- =darkroom-guess-margins= falls back to a generic percentage margin when =visual-line-mode= is on, when =variable-pitch-mode= is on, or when the buffer is empty.
- Since this config turns on =visual-line-mode= with Darkroom, the guessing path is less attractive here than it might look at first glance.

** =jay/darkroom-body-width=

Current config default: =80=

What it does:

- Controls the effective writing column width in the repo's custom fixed-width margin function.

Why test it:

- This is the cleanest way to answer "do I like Darkroom's layout?" without changing Darkroom's core behavior.

Try:

#+begin_src emacs-lisp
(setq jay/darkroom-body-width 72)
(jay/darkroom-refresh-current-buffer)
#+end_src

or

#+begin_src emacs-lisp
(setq jay/darkroom-body-width 90)
(jay/darkroom-refresh-current-buffer)
#+end_src

This is probably the first setting to play with if the current feel is "too narrow" or "too wide."

** =darkroom-fringes-outside-margins=

Package default: =t=

What it does:

- Controls whether fringes sit outside the writing margins.

Why test it:

- This is a lower-priority visual-taste setting, but it can slightly change how "page-like" the writing area feels.

Try:

#+begin_src emacs-lisp
(setq darkroom-fringes-outside-margins nil)
#+end_src

Then toggle Darkroom off and back on in the current buffer.

** =darkroom-margin-increment=

Package default: =0.05=

What it does:

- Controls how much =darkroom-increase-margins= and =darkroom-decrease-margins= change the margins each time.

Why test it:

- If =s-k o e= and =s-_= feel too jumpy or too subtle, this is the knob.

Try:

#+begin_src emacs-lisp
(setq darkroom-margin-increment 0.03)
#+end_src

or

#+begin_src emacs-lisp
(setq darkroom-margin-increment 0.08)
#+end_src

** =darkroom-verbose=

Package default: =nil=

What it does:

- Enables extra messages about Darkroom behavior.

Why test it:

- Mostly useful only if you want to inspect what it is doing while experimenting.

Try:

#+begin_src emacs-lisp
(setq darkroom-verbose t)
#+end_src

* A practical test sequence

If you want to decide quickly whether Darkroom is for you, this is the most useful experiment order:

1. Open a normal Org writing buffer in a single window and leave the config exactly as it is now.
2. Notice whether you like losing the mode line and header line.
3. Split the window and confirm whether the tentative behavior feels smart or annoying.
4. Use =s-k o e= and =s-_= a few times to see whether the current width feels basically right.
5. If the width is the only thing that feels wrong, experiment with =jay/darkroom-body-width= before judging Darkroom itself.
6. If the experience feels too visually similar to Olivetti, try =darkroom-text-scale-increase 1= or =2= and test again.
7. If what you really want is centered prose /without/ hidden status UI, that is a strong sign that Olivetti may still be the better fit.

* Signs that Darkroom is a good fit

- You like writing in a single window and want the rest of Emacs to visually disappear.
- You like the idea that focus mode automatically backs off when you split windows.
- You do not mind losing the mode line and header line while drafting.
- You want a stronger "I am in writing mode now" transition than Olivetti gives.

* Signs that Olivetti may be the better fit

- What you really want is just a centered text column.
- You want to keep the mode line and header line visible while writing.
- You work in split windows a lot and do not want the writing mode to change state automatically.
- You prefer a simpler, less opinionated writing surface.

* Bottom line

Darkroom is not automatically "better" than Olivetti. It is just more assertive.

If you want:

- centered text only, Olivetti is simpler
- centered text plus hidden status UI plus split-aware single-window focus behavior, Darkroom is more interesting

In this repo, the most important variables for evaluating Darkroom are probably:

- whether you like =darkroom-tentative-mode=
- whether you like hidden mode/header lines
- what body width feels right for =jay/darkroom-body-width=
- whether turning text enlargement back on makes Darkroom feel more purposeful
