#+TITLE: Whittle Transcript Review Workflow Plan

* Whittle Transcript Review Workflow Plan

** Problem
=whittle-transcript= in [[file+emacs:/Users/jay/emacs/emacs-settings/whittle.el][/Users/jay/emacs/emacs-settings/whittle.el]] is useful, but risky when run as a blind cleanup pass on spoken transcripts.

The core problem is that spoken filler can be syntactically or rhetorically necessary. Regex cleanup cannot reliably distinguish disposable filler from words that hold a sentence together.

Examples from the Narratively webinar cleanup:

#+begin_example org
Before:
Writing can be solitary, sitting alone, thinking, I mean, I love it, I think I'm good at it...

After:
Writing can be solitary, sitting alone, thinking I love it, I think I'm good at it...

Problem:
=I mean= was acting as a bridge. Removing it created =thinking I love it=.
#+end_example

#+begin_example org
Before:
It wants to just write it for you, you have to stop that behavior...

After:
It wants to just write it for you have to stop that behavior...

Problem:
The repeated =you= separated two clauses. It was not disposable.

Implementation note:
This one should be prevented by a targeted duplicate-word rule fix, not merely reported for review.
#+end_example

#+begin_example org
Before:
It's kind of like getting advice from a friend...

After:
It's getting advice from a friend...

Problem:
=kind of like= expressed analogy. Removing it changed the meaning.
#+end_example

#+begin_example org
Before:
What that is, is an automation step...

After:
What that is an automation step...

Problem:
The repeated =is= was grammatically necessary.

Implementation note:
This one should be prevented by a targeted duplicate-word rule fix, not merely reported for review.
#+end_example

#+begin_example org
Before:
I think it's kind of like a fantasy made-up scenario that, like, oh, like, I guess...

After:
I think it's a fantasy made-up scenario that oh I guess...

Problem:
The cleanup removed spoken setup words but left ungrammatical residue.
#+end_example

#+begin_example org
Before:
If Claude asks me questions like, hey, Jay... psychological safety, like. I, like, you defined it really clearly...

After:
If Claude asks me questions like, hey, Jay... psychological safety, like. I you defined it really clearly...

Problem:
The process removed filler without repairing an already rough transcript fragment, producing nonsense.
#+end_example

** Proposed Solution
Keep =whittle= in Elisp, and make the normal workflow edit-plus-report: the command applies cleanup to the buffer and also copies a before/after report to the clipboard for Codex verification and repair. Also fold in targeted rule fixes for bugs that can be eliminated cleanly.

Implement two changes:
1. Tighten duplicate-word collapse so it does not collapse comma-separated repeated function words such as =is, is= or =you, you=.
2. Make =whittle= and =whittle-transcript= apply cleanup and copy a Codex review report. Keep =whittle-transcript-report= as an explicit dry-run/report-only command.

The report command should:
1. Read the active region, or the whole buffer if no region is active.
2. Segment the original text into stable paragraph units before running cleanup.
3. Run the =whittle-transcript= pipeline on each unit in a temporary buffer, one pass at a time.
4. Snapshot each unit after each individual cleanup pass.
5. If a pass introduces a mechanical hazard, revert just that pass, record the held-back candidate edit, and continue the pipeline from the previous safe snapshot.
6. Coalesce safe per-pass changes into one report entry per changed unit.
7. Add a report summary with counts by risk tier, cleanup pass, and held-back hazard tag.
8. Apply the final safe per-unit after text to the source buffer for =whittle= / =whittle-transcript=, even when the unit also has held-back hazardous candidates.
9. Copy a compact report to the clipboard with =pbcopy=.
10. Save the full detailed report to a timestamped temp file for recovery.
11. Leave the source buffer unchanged only for explicit dry-run commands such as =whittle-transcript-report=.
12. Run a final-output scar scan over changed or hazard-touched units and report suspicious applied-output artifacts without changing the source again.

Jay's workflow:
1. Run =M-x whittle= or =M-x whittle-transcript= in Emacs.
2. The command changes the buffer and copies a compact before/after report to the clipboard.
3. Paste the clipboard contents into Codex.
4. Codex reviews the already-applied before/after report.
5. Codex reads the source file named in the report header and edits that file directly to repair any broken cleanup.
6. Jay reviews before committing.

The report is not an editable replacement transcript. The clipboard report should be compact; the full report in =/tmp= can contain every changed chunk. Codex uses the report as an audit lens over changes that have already been applied to the source file.

The scar scan is an audit lens too. It should flag patterns like orphan ellipses, fused clauses, suspicious case normalization, or damaged =right? So…= transitions, but it must not become another automatic rewrite pass.

** Pass Attribution
The report must show which cleanup pass caused each change.

Use segment-first attribution:
- Split the original source text into paragraph units before cleanup.
- Assign each unit a stable index and original starting line number.
- Run the full cleanup pipeline sequentially inside each unit.
- Record which passes changed that unit.

Define paragraph units as blank-line-delimited blocks. Treat org heading lines matching =^\\*+ = as boundaries and exclude the heading text itself from cleanup. Line-joining must stay within a unit, so it cannot merge across blank-line paragraph breaks or org headings.

Do not infer paragraph identity by diffing whole-buffer snapshots after each pass. Once the first pass changes text, later snapshots no longer match the source verbatim, which makes line lookup and multi-pass coalescing fragile.

Track these passes separately:
- =line-joining=
- =filler-chain collapse=
- =conservative filler removal=
- =sentence-edge filler removal=
- =em-dash false-start detection=
- =false-start collapse=
- =duplicate-word collapse=
- =punctuation cleanup=
- =case normalization=

If one paragraph is touched by multiple passes, the report should either:
- list one entry per pass, or
- show one final before/after entry with =Passes ::= listing all passes involved.

For v1, prefer one final entry per changed paragraph, with =Passes ::= included.

Boundary caveat:
Running cleanup per paragraph unit can differ slightly from running legacy whole-buffer cleanup. The main boundary-sensitive cases are line-joining and sentence-edge filler cleanup across paragraph breaks. The report header should state that the workflow is paragraph-unit based and may differ at unit boundaries.

Case-normalization caveat:
=whittle--normalize-case= historically capitalized the first lowercase character in the buffer or region. If report mode runs one paragraph per temp buffer, that can create spurious =case normalization= entries at the start of every unit. Implement report/apply mode so unit-initial capitalization is disabled or ignored unless the unit really follows a sentence boundary or org heading in the source context.

** Report Format
The report copied to the clipboard should be compact org-mode text.

#+begin_example org
* Whittle Transcript Review Report
- Source :: /absolute/path/to/source-file.org
- Generated :: [YYYY-MM-DD Day HH:MM]
- Command :: whittle-transcript
- Mode :: Cleanup has already been applied to the source buffer; this report is for Codex verification and repair.
- Changed units :: 120
- Applied units :: 120
- Held back :: 8 hazardous edits for review.
- Risk counts :: high 12; medium 31; low 80
- Applied pass counts :: duplicate-word collapse 4; conservative filler removal 52; punctuation cleanup 27; case normalization 19

** Instructions for Codex
Whittle has changed the current Emacs buffer, but the buffer may or may not already be saved to disk. First inspect the source path and confirm whether the reported applied changes are present. If they are present, continue without asking Jay to save again. If they are absent or cannot be confirmed, tell Jay to save the buffer and wait for confirmation before reviewing or repairing the source. Never tell him to discard, revert, or avoid saving the Whittle changes. Then review in this order: =Suspicious Output Scar Scan=, applied high/medium-risk changes, then held-back hazardous candidates. Scars are suspicious, not proof. Held-back candidate after text is not in the source; do not apply it just because it appears in the report. If an applied after version is wrong, edit the source file directly to repair that specific mistake. Flag only cases where the after version changed meaning, became ungrammatical, lost useful spoken cadence, or deleted necessary words. Use minimal fixes. Do not rewrite for style.

Risk categories:
- High risk :: =like=, =I mean=, =kind of like=, repeated function words if any still get collapsed, or any case normalization after a deletion.
- Medium risk :: sentence-edge filler removal, punctuation cleanup, false-start cleanup.
- Low risk :: =um= / =uh= removal, duplicate spaces, obvious filler-chain cleanup.

** Implementation Notes
- Do not convert =whittle.el= to Python.
- Implement this as an Emacs-native apply-plus-report workflow, with a separate explicit dry-run/report command available for debugging.
- Reuse the existing cleanup helpers, but run them one by one in a temp buffer so each pass can be attributed.
- Segment the original source first, then process each unit. Do not diff whole-buffer pass snapshots and try to reconstruct paragraph identity afterward.
- Define units as blank-line-delimited blocks, with org headings matching =^\\*+ = treated as boundaries and excluded from cleanup.
- Use paragraph-level changed chunks for v1. Perfect sentence segmentation is not required.
- Keep line-joining confined to the current unit.
- Include approximate line numbers from the original unit's starting location.
- Include summary counts at the top of the report by risk tier and by cleanup pass.
- Include summary counts for mechanical hazard tags.
- Copy a compact org report to the clipboard via =pbcopy=.
- Save the full org report to a timestamped recovery file under =/tmp=, using a name like =/tmp/whittle-transcript-review-YYYYMMDD-HHMMSS.org=, and include that path in the report header.
- The compact clipboard report should include a =Suspicious Output Scar Scan= section before applied high/medium-risk entries. Scar hits are advisory final-output warnings and should promote affected applied entries to high-risk review, but they should not change source text by themselves.
- The compact clipboard report should include high- and medium-risk before/after excerpts, summarize or drop low-risk details, show changed spans rather than whole paragraphs, use a small local context window around those spans, and avoid long repeated boilerplate.
- =whittle= and =whittle-transcript= should apply safe partial cleanup and copy the Codex report to the clipboard. Hazardous candidate edits stay in the report but are held back. A hazard in one part of a paragraph must not block safe cleanup elsewhere in that paragraph. The compact report should put =Suspicious Output Scar Scan= first, applied high/medium entries second, and =Hazard-Tagged / Not Applied= third. Do not make the primary commands report-only.
- Implement the duplicate-word fix as a small, separable checkpoint from the report command so it is easy to review or revert independently.
- For duplicate-word collapse, preserve comma-separated repeated function words such as =is, is= and =you, you=. Continue allowing genuinely safe collapses such as obvious stammers where the rule remains valid.
- For sentence-edge cleanup, preserve tag-question =right?= and sentence-opening =Like= because they often function as discourse or quote/example markers, not disposable filler.
- Treat =So…= / =So...=, sentence-initial =I mean,=, comma-bounded =like= before quote/example/clause boundaries, =right? So…= filler chains, and opener deletions that leave lowercase starts as hazards rather than auto-applied cleanup. Keep gates profile-aware where the risk is specific to aggressive transcript cleanup.
- If adding an option to =whittle--normalize-case= for report mode, default it so existing callers keep current behavior.
