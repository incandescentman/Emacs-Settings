* Prioritized changes

** 1. Make preview and apply agree

At lines 1805–1832, ~whittle-transcript-apply~ calls the mutating passes directly, bypassing paragraph segmentation and hazard checks. Route it through the existing report engine's cleanup decisions; suppress report output if needed, rather than changing which edits are accepted. Do the equivalent for ~whittle-apply~ and review the standalone filler and duplicate commands for the same bypass. Retain protection inside the individual helpers as well.

Success means that, for identical input and settings, the dry-run's proposed result and the applied text match exactly. This directly prevents the mismatch you encountered.

** 2. Turn off the broad em-dash deletion by default

At line 421, ~whittle--collapse-em-dash-false-starts~ deletes a fragment when it contains a comma, has at most ten words, and ends with an em dash followed by whitespace. Those conditions do not establish that the fragment is disposable. They delete the Oracle/IBM/Microsoft/Adobe/Google/Apple list, In October, and the qualification that emoji are not technically a language.

Keep ambiguous fragments as review candidates. The existing narrower repeated-prefix cleanup can continue handling its established restart cases. The tradeoff is that some genuine false starts remain for contextual review.

Also preserve the newline before every structural Org line. The current protected range starts at the heading itself, so an earlier deletion can consume its preceding newline without touching the protected characters. That is how the em-dash pass reproduced all three merged headings.

** 3. Separate filler removal from punctuation removal

The rules beginning at line 29 remove surrounding commas or consume arbitrary whitespace and punctuation. In this transcript they produce ~You can it's very good~ and ~We're actually usually I always use~. Remove the filler only when its surrounding syntax remains intact; preserve clause punctuation and prohibit matches crossing paragraph or heading boundaries.

Bare ~kind of like~ should not be an unconditional deletion: it can express comparison or approximation. The existing [[file+emacs:/Users/jay/emacs/emacs-settings/docs/whittle-transcript-review-workflow-plan.org][workflow plan]] already records this problem with an analogy about getting advice from a friend. Sentence-edge discourse markers are already disabled by default; apply the same contextual judgment here.

Use explicit horizontal spacing and deliberately selected punctuation for these rules. Emacs character classes can depend on the buffer's syntax table, another reason to test both actual Org buffers and the temporary buffers used by the report engine. See the [[https://www.gnu.org/software/emacs/manual/html_node/elisp/Char-Classes.html][GNU Emacs character-class documentation]].

** 4. Narrow duplicate collapse

At line 346, the duplicate matcher collapses arbitrary repeated words except for an exclusion list. It changes Bling Bling Dumpling to Bling Dumpling and removes expressive repetition such as whoa, whoa. Adding Bling to the exclusions fixes only this example.

Preserve plausible names and expressive repetition; hold uncertain content-word repeats for review. Continue automatically handling the narrow stutter cases already established by tests. Apply the same policy to the separate false-start pass so one helper cannot undo another helper's protection.

** 5. Make the report describe its evidence precisely

In dry-run mode, label results proposed rather than applied. Replace safe partial with accepted partial, and describe zero scars as no known scar patterns detected. The current scan missed meaningful losses; its result is not a fidelity judgment.

Include the input buffer's content hash, the proposed/applied output hash, the cleanup profile, and the code version. A path alone cannot establish whether a pasted report describes the current saved file or a different buffer state.

As a follow-up, track individual replacements and their locations. The current hazard comparison uses tag presence, while changed-span tracking encompasses everything between the first and last change in a pass. That can conflate separate edits. Risk ranking also marks a whole paragraph high merely because it contains like, even if that word was untouched. Assessing the actual replacement would make the review more useful and allow harmless edits to proceed independently.
