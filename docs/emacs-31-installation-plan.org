** Build an installable Emacs 31
Done in staging, 2026-10-31: /Users/jay/src/emacs31-staging/Emacs-31.app (142 MB), bundle ID ~org.gnu.Emacs.31~. At switchover it was copied to /Applications/Emacs-31.app with ~ditto~, and the two existing Emacs preferences (~ApplePressAndHoldEnabled~ off, ~NSAutomaticPeriodSubstitutionEnabled~ off) were copied to the new ID so key repeat behaves the same. The cask's /Applications/Emacs.app was not touched. The staging copy was then renamed [[file+emacs:/Users/jay/src/emacs31-staging/Emacs-31.app.staged][Emacs-31.app.staged]] and removed from Launch Services (~lsregister -u~), so that only the installed copy answers to ~org.gnu.Emacs.31~; macOS had registered it under that ID and kept tracking it after the rename until it was unregistered again.

How it was built, so a rebuild can repeat it:
1. A clean clone of the PR #157 branch at commit ~14ce5f2e~, in [[file+emacs:/Users/jay/src/emacs-mac-pr157-install/][emacs-mac-pr157-install]], configured with the trial's features plus ~--enable-mac-self-contained~ and ~--enable-mac-app=/Users/jay/src/emacs31-staging~; the full configure line is in [[file+emacs:/Users/jay/src/emacs31-staging/configure.log][configure.log]]. It also adds ~--without-rsvg~: Emacs 29 has no librsvg either and shows SVG through macOS, and the staging build does the same.
2. ~make~ and ~make install~, which wrote only into the staging folder.
3. In this build only two Homebrew libraries are linked, gnutls and tree-sitter; libxml2 and sqlite3 come from macOS. ~dylibbundler -cd -b -x MacOS/Emacs -d Frameworks/ -p @executable_path/../Frameworks/~, run from ~Contents~, copied those two and their eight dependencies into ~Contents/Frameworks~. Its own signing step fails, which is expected (see 5).
4. Set ~CFBundleIdentifier~ to ~org.gnu.Emacs.31~ and rename the app to Emacs-31.app. Both have to happen before the app is ever launched, so that macOS never registers a second app as ~org.gnu.Emacs~. The build also leaves its own copy at ~mac/Emacs.app~ in the source folder, with the ~org.gnu.Emacs~ ID, and macOS registered that copy without its ever being launched. Give it a separate ID (here ~org.gnu.Emacs.pr157-install-build~) and re-register it with ~lsregister -f~. Then check that the ~lsregister -dump~ output lists only /Applications/Emacs.app as ~org.gnu.Emacs~ (plus its copy on the Carbon Copy backup volume).
5. Re-sign and seal the app. Rewriting library paths breaks the program's signature, and macOS kills an unsigned program at launch ("Code Signature Invalid"). Two things in the installed layout stop ~codesign~ from sealing the app as a whole. The helper folder ~Contents/MacOS/libexec/aarch64-apple-darwin27.0.0~ has dots in its name, so ~codesign~ takes it for a nested bundle. And three files among the programs are not programs: ~Emacs.pdmp~ and ~rcs2log~ in that folder, and ~Emacs.sh~. So:
   - Rename the folder to ~libexec/helpers~ and leave a symbolic link under the old name, because Emacs has that path built in.
   - Sign ad hoc (~codesign --force -s -~) each library in ~Frameworks~, each file in ~bin~ and ~libexec/helpers~, and ~Emacs.sh~. The three non-program files get their signatures in extended attributes, as in the cask's Emacs 29.
   - Sign the app itself with ~codesign --force -s - Emacs-31.app~, without ~--deep~.
   ~codesign --verify --deep --strict~ then reports "valid on disk" and "satisfies its Designated Requirement", with Info.plist bound and 4,452 files sealed.

Verified 2026-10-31 under a sandbox that blocked reading ~/opt/homebrew~, ~/usr/local~, both build folders, and the pre-bundling copy, and refused writes to the home folder: every path Emacs reports (~exec-directory~, ~data-directory~, the Lisp files) is inside the app; tree-sitter loads the grammars in ~~/.emacs.d/tree-sitter~ and parses; libxml2, sqlite3, modules, xwidgets, and SVG, PNG, JPEG, GIF, and TIFF images are available; the hexl helper and the app's emacsclient run; GNU ELPA and MELPA download over TLS with certificate checking on (~gnutls-verify-error~), so the certificates came from macOS, since Homebrew's were blocked; and a GUI window opened and answered on its own socket. While it ran, every library outside macOS that it had loaded came from ~Contents/Frameworks~. Results are in [[file+emacs:/Users/jay/src/emacs31-staging/batch-checks.txt][batch-checks.txt]]. The app was first verified with each program signed but the bundle unsealed; after sealing, the checks and the window test were run again with the same results. Afterward the launch routes, the cask app, init.el, and Launch Services' ~org.gnu.Emacs~ all matched [[file+emacs:/Users/jay/src/emacs31-staging/route-baseline.txt][route-baseline.txt]], and the Org, Emacs Lisp, text, and Markdown file defaults still named ~org.gnu.Emacs~.

* Known limitation: quitting can fail in persp-mode's exit save
With ~dotspacemacs-persistent-server~ on, ~s-q~ and ~C-x C-c~ hide the window instead of quitting. Results in the Emacs 31 trial, 2026-10-31:
- With the window visible, a real exit (~save-buffers-kill-emacs~ with ~spacemacs-really-kill-emacs~ bound to t) completed in about a second.
- With the window hidden by ~s-q~'s command, the same real exit failed twice out of two attempts: persp-mode's layout autosave raised "Window too small to accommodate state" in ~window-state-put~, Emacs opened the debugger, and it kept running.
- With the window hidden, an application quit request (~osascript -e 'quit app id "org.gnu.Emacs.pr157-trial"'~) was declined: AppleScript reported "User canceled" (-128), and Emacs stayed running, hidden, with no error. This tests an application quit request only; it does not establish what happens during macOS logout or shutdown.

Emacs 29 comparison, 2026-10-31: the cask's Emacs 29.4 ran as an isolated, sandboxed instance on the trial configuration with a copy of the 29-compiled packages, its own server socket (~trial29~), and was addressed only by that socket and its verified PID, never by app ID. Conclusion: the exit failure already exists on Emacs 29 with this configuration. In the trial it appeared only with the window hidden, but on the real configuration it also appeared with the window visible (next paragraph), so it is not established as a hidden-window problem and what triggers it is unknown. It is not caused by Emacs 31 and does not block the switch. (Corrected 2026-11-01; this conclusion first called it the hidden-window exit failure.) Fixing it is separate work for either version; candidates include catching errors in persp-mode's exit autosave, or skipping window state in that save.

Real configuration, Emacs 29, 2026-11-01: when Emacs 29 was closed after the switch, its real exit raised the same persp-mode error and opened the debugger with the window visible, so the failure does not need a hidden window. Why it opened a dialog, and why it then exited, are unknown. Before either attempt it had no modified file buffers, no capture or clock in progress, and nothing in the minibuffer.
