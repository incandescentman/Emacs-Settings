* 2026-05-03: Two follow-up fixes for the Fountain =s-p= export
- *Bug 1 — keymap precedence:* the original =s-p= binding lived in =my/fountain-mode-bindings= and was installed into =fountain-mode-map= via =my/install-mode-bindings=. It never fired in Fountain buffers; =org-export-dispatch= (the global =s-p=, installed into =key-minor-mode-map= by =my/global-key-bindings=) won every time. Reason: =key-minor-mode= is a *minor mode*, and minor-mode keymaps take precedence over major-mode keymaps, so any global binding shadows the corresponding major-mode binding. /This is a config-wide trap, not Fountain-specific./
- *Fix:* added =my/fountain-install-key-minor-overrides= in [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]] (hooked from =fountain-mode-hook= inside the existing =with-eval-after-load 'fountain-mode= block). The hook builds a buffer-local keymap parented to =key-minor-mode-map=, defines =s-p= → =jay/fountain-export-and-open= on it, and installs it via =minor-mode-overriding-map-alist=. That mechanism is Emacs's explicit per-buffer override slot and beats =key-minor-mode-map= in Fountain buffers only. Reverted =my/fountain-mode-bindings= back to plain =my/writing-mode-bindings= since the =s-p= entry there was dead code; replaced with a docstring note pointing at the override map so the next reader doesn't repeat the mistake.
- *Bug 2 — closure capture:* the first export attempt died with =Debugger entered--Lisp error: (void-variable pdf)=. The sentinel lambda in =jay/fountain-export-and-open= referenced =pdf= from its enclosing =let*=, but [[file+emacs:/Users/jay/emacs/emacs-settings/gnu-emacs-startup.el][gnu-emacs-startup.el]] does not have a =;;; -*- lexical-binding: t -*-= header, so the lambda is not a closure under dynamic binding — when =let*= unwound, =pdf= disappeared, and the sentinel later ran with =pdf= unbound.
- *Fix:* in [[file+emacs:/Users/jay/emacs/emacs-settings/gnu-emacs-startup.org][gnu-emacs-startup.org]], stash the PDF path on the process object via =(process-put proc 'fountain-pdf pdf)= before installing the sentinel, and retrieve it inside the sentinel via =(process-get p 'fountain-pdf)=. Works regardless of binding mode and avoids the deprecated =lexical-let=.
- Documented both bugs in [[file+emacs:/Users/jay/emacs/emacs-settings/docs/codebase-wisdom.org][docs/codebase-wisdom.org]] under two new entries: /=key-minor-mode-map= Wins Over Major-Mode Keymaps/ and /Process Sentinels In Dynamically-Bound Files Can't Capture =let*= Bindings/. Both are repeatable traps that apply beyond Fountain — the first to any major mode that wants to override a global =key-minor-mode-map= binding, the second to any async callback in a non-lexical Elisp file.
- Verified end-to-end with an isolated batch test that re-defined the function in a stub =fountain-mode=, ran a real export against a synthetic =.fountain= file, and confirmed (a) the process exited 0, (b) the PDF was created, (c) the sentinel ran without =void-variable=, and (d) the sentinel correctly retrieved =pdf= via =process-get=. Jay then confirmed live in Emacs that =s-p= now does the right thing.

* 2026-05-03: Make =s-k u p= Org-aware so drawers keep their line breaks
- Replaced the raw =unfill-paragraph= binding behind [[file+emacs:/Users/jay/emacs/emacs-settings/keys.el][keys.el]]'s =s-k u p= with a new [[file+emacs:/Users/jay/emacs/emacs-settings/spacecraft-mode.org][spacecraft-mode.org]] helper, =jay/unfill-paragraph-dwim=.
- Why: the upstream =unfill.el= command calls plain =fill-paragraph= with a huge =fill-column=, which bypasses Org's own structure-aware filler and can collapse non-prose lines such as property drawers.
- Fix: in Org buffers, the new helper now uses =org-fill-paragraph= with =fill-column= set to =most-positive-fixnum=. Outside Org, the helper falls back to plain =fill-paragraph= / =fill-region= behavior.
- This keeps the nice one-key workflow while making the smart behavior come from Org itself instead of hand-rolled regex exceptions.
